Most <Term id="rag">RAG</Term> problems I'm asked to fix turn out to be chunking problems. The model is fine. The search is fine. But the passage that answers the question was split across two chunks, or buried in a chunk so large its meaning got averaged away, or cut off from the heading that explained what it was about.

<Term id="chunking">Chunking</Term> decides the unit your system retrieves — and so the unit your model gets to read. Get it wrong and no amount of prompt work will save you.

## Why chunk size is a trade-off

Every chunk gets turned into one <Term id="embedding">embedding</Term>. That creates a tension:

- **Small chunks** match questions precisely, because each one is about one thing. But they lose context — a sentence like "the dose was then doubled" means nothing without what came before.
- **Large chunks** keep context, but their embedding becomes a blur of several topics, so they match fewer questions well. They also cost more tokens every time you retrieve one.

There isn't one right size. There's a right size *for your documents and your questions*, and the strategies below are different ways of getting out of the trade-off.

## What each one actually does

### Fixed-size with overlap
Cut every N tokens, overlapping by 10–20% so sentences on a boundary appear in both chunks. Fast and predictable, and it ignores meaning entirely. I use it as a baseline to beat, not as a final answer.

### Recursive, separator-aware
Try to split on the biggest natural boundary first — sections, then paragraphs, then sentences — and only fall back to smaller ones when a piece is still too long. It respects the text's own shape for almost no extra cost. This is where I start for plain prose.

### Structure and layout-aware
Parse the document properly first: headings, lists, tables, page numbers, form fields. Then chunk along that structure — a table stays whole, a section stays with its heading. For PDFs, scans and forms this is the single biggest improvement you can make, and it's the one teams most often skip because parsing is unglamorous.

### Semantic breakpoints
Embed each sentence, and start a new chunk where the similarity between neighbouring sentences drops — where the topic changes. Useful for long unstructured text like transcripts or narrative notes. It costs an embedding call per sentence at ingestion time and the thresholds need tuning.

### Parent–child (small-to-big)
Index small chunks for precise matching, but when one matches, hand the model its larger parent — the paragraph or section it came from. You get the precision of small chunks and the context of big ones. This is my usual second step after structure-aware chunking.

### Contextual chunk headers
Before embedding, prepend a short description of where the chunk sits: the document title, the section path, and optionally a one-sentence summary of the surrounding context generated by a model. Anthropic published this as *contextual retrieval* and reported large drops in retrieval failures, especially combined with <Term id="bm25">BM25</Term> and a <Term id="reranker">reranker</Term>. The cost is a model call per chunk at ingestion — manageable with prompt caching, but real.

### Late chunking
Run the *whole document* through a long-context embedding model first, then pool the token embeddings into chunk vectors afterwards. Each chunk's vector has "seen" the rest of the document, so pronouns and references keep their meaning. Jina AI introduced the technique. It needs an embedding model that supports it and long inputs, which is why it scores lowest on simplicity.

<Callout tone="tip" title="The cheapest big win">
Before trying anything clever, put the document title and section heading at the top of every chunk. It's a few lines of code, it costs nothing at query time, and it fixes a surprising share of "the right passage exists but never comes back" failures.
</Callout>

## The order I try them in

<Steps>
  <Step title="Look at the documents before choosing anything">
    Open twenty real files. Are there headings? Tables? Scans? Forms? Long narratives? The answer decides most of what follows, and it takes an hour.
  </Step>
  <Step title="Start structure-aware, recursive underneath">
    Parse the structure, split along it, and use recursive splitting inside any section that's still too long. Put the title and section path on every chunk.
  </Step>
  <Step title="Build a small eval set now, not later">
    Fifty to a hundred real questions, each with the passage that answers it. Without this you're comparing strategies by feel.
  </Step>
  <Step title="Add parent–child if answers need context">
    If the right chunk comes back but the model still answers badly, it's probably missing surrounding context. Retrieve small, read big.
  </Step>
  <Step title="Add contextual headers or late chunking if chunks don't stand alone">
    If the right chunk *doesn't* come back because it only makes sense in context, give each chunk that context before it's embedded.
  </Step>
</Steps>

## A starting point in code

A sketch of structure-aware chunking with parent–child retrieval. Real parsers are messier, but the shape holds:

```python
def chunk_document(doc, max_tokens=400):
    chunks = []
    for section in doc.sections:              # from a layout-aware parser
        header = f"{doc.title} > {' > '.join(section.path)}"
        parent_id = store_parent(section.text)  # the full section, for reading
        for piece in recursive_split(section.text, max_tokens):
            chunks.append({
                "text": f"{header}\n\n{piece}",   # what gets embedded
                "parent_id": parent_id,           # what the model reads
                "page": section.page,             # for citations
            })
    return chunks

def retrieve(query, k=8):
    hits = hybrid_search(query, k=k * 3)      # vector + BM25
    hits = rerank(query, hits)[:k]
    parents = dedupe(h["parent_id"] for h in hits)
    return [load_parent(p) for p in parents]
```

## Sizes to start from

Treat these as a first guess to measure against, not rules:

- **Chunks for matching:** 200–500 tokens for precise questions; larger for summary-style questions.
- **Overlap:** 10–20% if you're splitting mid-text; none needed when you split on real boundaries.
- **Parents for reading:** a full section, capped so that *k* parents fit comfortably in the model's <Term id="context-window">context window</Term> with room for the answer.

## How to tell if it's working

Measure retrieval separately from answers. If the right passage isn't in the top results, no prompt will fix it.

- **Recall@k** — for each eval question, is the answering passage in the top *k*? This is the number I watch most.
- **MRR** — how high up the right passage appears. Matters when you pass few chunks to the model.
- **Answer quality** — graded against a rubric, only once retrieval looks healthy.

Run the whole set every time you change chunking. A change that helps one kind of question often quietly hurts another.
