Standard <Term id="rag">RAG</Term> treats a document as a pile of interchangeable chunks. Ask a question, pull the eight most similar pieces, hand them to the model. For a short document, or a question with a single answer in a single place, that works.

It falls apart on long documents — a 400-page annual report, a contract with its schedules, a technical manual — because many real questions aren't about one place:

- **Global questions:** "What are the main risks this report describes?" No single chunk contains the answer.
- **Cross-reference questions:** "Does the exclusion in section 9 apply to the case in schedule C?" The answer needs two distant parts read together.
- **Where-is-it questions:** "Which section covers termination?" The answer is about the document's structure, which chunking threw away.

The fix is to keep the structure and give the system a map.

## Why each piece is there

### Keep the structure the document already has
Long documents are almost always organised: chapters, sections, schedules, appendices. That organisation is information — it tells you what belongs together and where things are. A layout-aware parser that keeps headings and page numbers is the foundation. If your parser flattens everything to text, fix that first.

### Summaries answer the questions chunks can't
A global question needs a view of the whole. Summarising bottom-up gives you that view at every level: a summary per section, per chapter, and for the document. This is close to the RAPTOR approach — recursive summarisation into a tree — except that for well-structured documents I build the tree from the document's own headings rather than by clustering.

### Routing avoids doing everything for every question
Most questions are local. Sending every question down the expensive global path wastes tokens and often answers worse, because summaries lose detail. A cheap routing step keeps simple questions simple.

### Order matters more than people expect
Retrieval returns pieces ranked by similarity. If you paste them into the prompt in that order, the model reads events out of sequence and references before the thing they refer to. Re-sorting by document position, with a breadcrumb on each piece, is one of the cheapest quality gains in this design.

<Callout tone="note" title="Build the eval set around global questions too">
Most RAG eval sets are full of "find the fact" questions, because they're easy to write. Make sure a third of yours are global or cross-reference questions — otherwise you'll never see the failures this design exists to fix.
</Callout>

## When not to build this

Context windows are large now. If a document fits comfortably in one, and you'll ask it only a handful of questions, just give the model the whole thing — with prompt caching if you'll ask more than once. It's simpler and it often answers better.

The hierarchical design earns its complexity when documents are long, structured and queried many times — a contract a team negotiates over for weeks, a manual thousands of employees search.

## A sketch of the query path

```python
def answer(question, doc_id):
    kind = route(question)                  # "local" | "cross_ref" | "global"

    if kind == "global":
        nodes = search(question, doc_id, level="summary", k=6)
    elif kind == "cross_ref":
        nodes = search(question, doc_id, level="any", k=12)
        nodes = expand_to_sections(nodes)   # read whole sections, not fragments
    else:
        nodes = search(question, doc_id, level="passage", k=8)

    nodes = sorted(dedupe(nodes), key=lambda n: n.position)
    context = "\n\n".join(
        f"[{n.section_path} · p.{n.pages}]\n{n.text}" for n in nodes
    )
    return generate_with_citations(question, context)
```

## Things that go wrong

- **Summaries that drift.** A summary can state something the source doesn't. Keep summaries extractive where you can, and always let a summary hit expand to its source text before the final answer.
- **Bad parsing, silently.** A missed heading merges two sections; a table read row-by-row becomes nonsense. Spot-check parser output on real files before tuning anything else.
- **Re-summarising on every change.** When a document is updated, only rebuild the summaries on the path from the changed node to the root.
